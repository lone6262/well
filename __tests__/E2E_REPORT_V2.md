## 一、E2E 可行性分析

### 1.1 为什么标准 E2E 测试不适用

微信小程序的封闭生态导致标准 Web E2E 测试框架（Playwright、Cypress、Puppeteer）无法直接使用：

#### 技术限制

| 限制项 | 说明 | 影响 |
|--------|------|------|
| **运行环境** | 小程序运行在微信客户端容器内，非标准浏览器环境 | 无法使用 DOM 选择器、浏览器 API |
| **协议差异** | 使用微信自定义协议 `wx://` 而非 HTTP/HTTPS | 无法直接通过网络拦截测试 |
| **鉴权机制** | 微信登录体系，依赖 `wx.login()` 获取 code | 无法自动化获取微信登录凭证 |
| **支付流程** | 微信支付是原生流程，JSAPI 调起原生支付 | 无法模拟真实支付环境 |
| **真机依赖** | 许多 API（位置、相册、授权）需真机测试 | 模拟器测试覆盖率不足 |

#### 对比标准 Web E2E

```
标准 Web E2E:
浏览器 → HTTP请求 → DOM渲染 → 自动化测试工具

小程序 E2E:
微信客户端 → 小程序容器 → 云开发 → 微信服务端 → (无直接测试入口)
```

### 1.2 替代测试方案

#### 方案对比

| 方案 | 适用场景 | 优势 | 劣势 |
|------|----------|------|------|
| **微信开发者工具自动化** | 回归测试、冒烟测试 | 官方支持、可模拟真机 | 需学习成本、稳定性一般 |
| **真机手动测试** | 完整用户流程验收 | 最接近真实环境 | 人力成本高、不可重复 |
| **云函数 API 测试** | 后端逻辑验证 | 可自动化、覆盖率高 | 无法覆盖前端交互 |
| **单元测试** | 业务逻辑验证 | 快速反馈 | 无法覆盖集成场景 |

#### 推荐策略

```
P0 核心流程: 真机手动测试（每次发版前）
P1 重要功能: 微信开发者工具自动化
P2 边缘场景: 云函数 API 自动化
全量逻辑: 单元测试（Jest）
```

### 7.1 数据库集合清单

| 集合名 | 用途 | 关联 |
|--------|------|------|
| `users` | 用户信息 | 所有模块 |

| `articles` | 知识库文章 | 无 |
| `invites` | 邀请记录 | 用户 |

### 7.2 云函数调用链路

```
用户登录:
  app.js → wx.login() → silentLogin 云函数 → 返回 token + openid

症状自查:
  提交表单 → submitSymptom 云函数 → 规则引擎 → 保存记录 → 返回风险评估

创建订单:
  createOrder 云函数 → 检查额度 → 扣减额度 → 创建订单 → 返回支付参数

支付回调:
  微信支付 → payCallback 云函数 → 更新订单 → 激活会员 → 生成报告

管理员登录:
  adminLogin 云函数 → 验证密钥 → 生成 Token → 返回管理员 Token
```
